# Changelog

Lawcheck follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Before you upgrade

- `scope.law_changes` in `lawcheck check --json` no longer says `changes may_use` for a `may_use` list that got wider, or `changes the waivers` for a type whose waivers count again. It says `widens may_use of the type library by command` or `widens may_use of the type library to any file`, and `reads waivers in the type library`. A script that finds these changes by the old words also looks for `widens may_use` and `reads waivers`.
- Lawcheck now reads `.lawcheck/config.local.yaml` as the reviewer settings of one machine. In alpha.5 no command read that file. `lawcheck check` stops with `config-invalid` on a `.lawcheck/config.local.yaml` that git tracks: take it out of git with `git rm --cached .lawcheck/config.local.yaml`, or move its settings into `.lawcheck/config.yaml`. An untracked one now sets the reviewer on its machine, and a key outside its `reviewer` section is `config-invalid`.

### Notes of 0.1.0-alpha.5, corrected

The notes of 0.1.0-alpha.5 are wrong in ten places. One is under Fixed below, and one under Security. These lines correct the other eight:

- The messages of the Claude Code plugin about a check, a waiver, a change to the law or a missing reviewer start with `Lawcheck:`. Three messages at the start of a session do not. In a folder with no law the message starts "The Lawcheck plugin is on". With a wrong `runner`, or when `lawcheck prime` did not run, it starts "This repository has a Lawcheck law". The notes said every message starts with `Lawcheck:`.
- `lawcheck doctor` reads the uses of the files whose `may_use` list is in force, as `check --full` does. Under a law with no `may_use` it reads no use and names no configuration file. The notes said it reads the uses of every file.
- A push in GitHub Actions or Azure Pipelines takes its base from `--base`, from `LAWCHECK_BASE` or from `origin/HEAD`. The notes said it needs `--base`.
- With a reviewer rule and no reviewer set, alpha.4 already said so in `lawcheck doctor`, and a check on your machine failed with `not-reviewed`. The line in `lawcheck prime` and the message of the Claude Code plugin are what alpha.5 adds. The notes said that nothing in alpha.4 said so until CI failed.
- In Copilot CLI the output of a hook has no field for a message to you. A hook can print progress lines to the timeline of the session, and the plugin prints none, so its messages reach you through the agent. The notes said that Copilot CLI gives a plugin no way to write to you.
- The setup skill proves a `may_use` list or a rule with a probe file that must fail. Two kinds of type get no probe: a type whose paths take no new file, and a type whose list names every type it could use. The notes said it checks each list.
- The note of `lawcheck check` about the waivers a change adds names up to five of them and counts the rest. The note about a change to the law does the same with its items. It shows first only some of the items that loosen the law, such as a rule taken off a type, so a widened `may_use` list can stay in the count. `--json` lists them all. The notes said the note names each one.
- `untyped-file` covers a file in a new folder only when a pattern of `required` matches it. Outside those patterns, a file that no type takes is still no finding. The notes said that code in a new folder beside the layers no longer escapes the law.

### Added

- One machine can use its own reviewer without a commit. Each key of the `reviewer` section has a variable, such as `LAWCHECK_REVIEWER_PROVIDER` and `LAWCHECK_REVIEWER_MODEL`, and `.lawcheck/config.local.yaml`, which git ignores, takes the same keys. A variable wins over `.lawcheck/config.local.yaml`, which wins over `.lawcheck/config.yaml`. `lawcheck doctor` and `lawcheck explain --rule` name the reviewer in force and the place of each value. With `--json`, the rule document of `lawcheck explain` has the new field `reviewer`. A pass counts whatever reviewer recorded it. `lawcheck docs config` describes both places under "On one machine".
- The law that judges a change in CI is now your team's choice in `lawcheck docs ci`: the change's own law, the law of the base with `--law-from`, or both, which the workflow runs as written. The page gives the lines for each choice and says what a choice of one law misses. With the law of the base alone, for example, a change that breaks the law file passes, and once merged it stops every later check by that law, the check of its fix too. A coding agent that sets up the job is told to ask you which first, in `lawcheck docs ci` and `lawcheck docs agent-setup`, and a setup writes the job only if you ask.

### Changed

- `lawcheck docs changelog` prints at most 30,000 characters. A longer changelog prints its newest section whole, then the releases before it, newest first, until one does not fit, then a line that names the whole changelog: `docs/changelog.md` in the installed package and https://docs.lawcheck.dev/changelog.html. The line of the next page stays last. `--json` gives the whole page.
- The scripts that show findings on a pull request have a page of their own, `lawcheck docs ci-findings`: annotations on GitHub, a code quality report on GitLab, and GitHub code scanning. In alpha.5 they were a section of `lawcheck docs ci`, which now links the new page.

### Fixed

- On Windows, after a run that was calling a program reviewer such as `claude-code` is killed, Lawcheck no longer ends a process that another program started under the reviewer program's id after Lawcheck saw that the run was gone. In alpha.5 it could, when that other program had already ended, or when Windows had given the id to a third process, by the time Lawcheck looked. The notes of 0.1.0-alpha.5 said that Lawcheck ends only the processes it started.
- When a change to the law has more than five items, the note of `lawcheck check` now shows a widened `may_use` list before the items that can't loosen the law. In alpha.5 it could stay in the count. The note and `scope.law_changes` now name such a change `widens may_use of the type library by command`, where alpha.5 wrote `changes may_use of the type library` for a wider list and a narrower one alike. A type whose waivers count again is `reads waivers in the type library`. `lawcheck docs change` gives the full order, which also covers other changes that may loosen the law and patterns that start with `!`.
- A line you add below the check in the pre-commit hook of `lawcheck docs ci` now runs. In alpha.5 it never did. If you use that hook, copy it again.

### Security

- The notes of 0.1.0-alpha.5 said that, with the second check of `lawcheck docs ci`, a pull request that adds a signer of its own or takes `signers` out fails. That check reads the signers of the base. A pass that the pull request signed with its own key, or left unsigned, is therefore `not-reviewed`, and the check fails on the file of that pass. A pull request that changes only `signers` passes both checks, and its note names the change, such as `adds the signer mallory`. Once it is merged, the passes of that signer count. After the merge of a pull request that takes `signers` out, every pass in `.lawcheck/verdicts` counts, signed or not. Ask for a code owner's review of `.lawcheck/`, as `lawcheck docs ci` says under "A change to the law".

## [0.1.0-alpha.5] - 2026-11-25

### Before you upgrade

- A law that uses one of the new keys `signers`, `required` or `ignored`, or a rule that names a `companion`, stops alpha.4 with `law-invalid`. Install alpha.5 on every machine, CI job and git hook that checks the repository before you add one.
- A rule whose id is one of the new codes `law-from-unreachable`, `law-from-packages` and `not-a-signer` stops alpha.5 with `law-invalid`. Give such a rule another id, and its file the same name, before you upgrade.
- A use that could name several files is now a `forbidden-use` when the `may_use` list forbids every one of them, such as a Java star import of a package whose files lie in two forbidden types, or a C# partial class spread over two forbidden types. In alpha.4 such a use only counted as unresolved, so a check that passed there can fail now. The message names the files with their types. Add one of the types to `may_use`, or waive the use with its reason. A use with one allowed file among its candidates still passes.
- The workflow of `lawcheck docs ci` now checks the second time with `lawcheck check --base "$base" --law-from "$base"`. Its alpha.4 version checked out the base's `.lawcheck/law.yaml` and `.lawcheck/rules/` and ran a plain check. When you replace those lines with the new one, a base rule that imports the project by its own `name` or imports a name that starts with `#`, and so reaches a file outside `.lawcheck/rules/`, stops that check with `rule-crashed`. The error names the import and the file. Copy what the rule needs of that file into `.lawcheck/rules/lib/`, import it from there by a relative path, and merge that change into the base first. A file git lists in `.lawcheck/node_modules` or `.lawcheck/.local` stops the same check with `law-from-packages`.
- `scope.law_changes` in `lawcheck check --json` no longer lists the waivers a change adds. A script that read them there reads the items of `waivers` whose `added` is true.
- A `check` or `try` that ends with exit 2 after it sent requests to a reviewer ends its first line with the count, such as `lawcheck: ERROR  1 error, 2 reviewer calls`, and the document `lawcheck-error/1` gains `calls_made`. A program that checks the document against a schema that refuses unknown keys has to allow `calls_made`.

### Added

- The plugins for Claude Code, Codex and GitHub Copilot CLI have a skill that writes the first law of a repository with you: `/lawcheck:setup` in Claude Code and in Copilot CLI, `$lawcheck:setup` in Codex. Only you start it, by typing the command. The agent describes the folders as types, writes the `may_use` lists that the code already keeps, and asks you before it forbids a use that the code already makes. It writes a script rule only from a rule your repository wrote down or a convention that every file keeps, and checks that each list and each rule fails on a file that breaks it. It changes nothing outside `.lawcheck/` and commits nothing unless you ask. When you ask for advice, it writes `.lawcheck/advice.md` with at most three things that the code does not hold today, and three more when you ask for more. When you name where the code should get to, it writes `.lawcheck/target.md` with that law and at most seven steps to reach it. Lawcheck reads neither file.
- Any other coding agent follows the same steps from `lawcheck docs agent-setup`: tell it "Run `lawcheck docs agent-setup` and follow it." In a folder with no law, `lawcheck prime` points the agent at that page, and the plugin tells the agent to write no law on its own. The agent tells you the command that starts the skill instead.
- A script rule can read its file's syntax tree with `await file.tree()` and the uses that `may_use` judges with `await file.uses()`, each use with the file it reaches and that file's type. Lawcheck reads either one only when the rule asks, so a rule that asks for neither costs what it cost in alpha.4. For a file over 512 KiB, a language Lawcheck cannot read or a parse that fails, the rule gets no tree and no uses, and `absent` says which of the three it was. `lawcheck explain <file> --tree` prints the tree of a real file before you write the rule, and `lawcheck docs write-a-script-rule` ends with a rule that reads the tree, so a `fetch()` in a comment is no finding.
- A reviewer rule can name a `companion`, a module in `.lawcheck/rules/lib/` that returns the files that go into the prompt of each judged file alone, such as each test with its spec. A change to the companion or to a file it returned makes the verdicts it fed stale. `lawcheck explain` runs the companion of a rule that has one, and a rule without one keeps its verdicts. `lawcheck docs reviewer-rules` has an example.
- `lawcheck check --law-from <ref>` judges a change by `.lawcheck/law.yaml`, `.lawcheck/config.yaml`, `.lawcheck/rules/` and the `package.json` files of another commit, so a change that loosens its law and breaks it fails. `lawcheck docs commands` says what it reads from that commit.
- A plain `lawcheck check` in GitHub Actions, GitLab CI and Azure Pipelines finds its base from the variables of the pull request: `GITHUB_BASE_REF`, `CI_MERGE_REQUEST_TARGET_BRANCH_NAME` (and `CI_COMMIT_BEFORE_SHA` for a push) and `SYSTEM_PULLREQUEST_TARGETBRANCH`. `--base` and `LAWCHECK_BASE` still come first, and the variable comes before `origin/HEAD`. In alpha.4 the first run in CI stopped with `base-unreachable` until you added `--base`. A push in GitHub Actions or Azure Pipelines still needs `--base`.
- `lawcheck check --strict` judges every file as `--full` does, and a finding in old code fails the run with exit 1 when the same finding in the change would. A team that paid its debt can keep it at zero.
- `lawcheck check --sarif <file>` also writes the findings in SARIF 2.1.0 for GitHub code scanning. `lawcheck docs ci` has the step that uploads it.
- The law takes two keys at the top, `required` and `ignored`, each a list of patterns. A text file under `required` that no type takes is the new finding `untyped-file`, so code an agent puts in a new folder beside the layers no longer escapes the law. A file under `ignored` has no type. `lawcheck explain` and `lawcheck prime` name both.
- `lawcheck check` names each waiver that a change adds in a note under the first line, such as `note: this change adds 1 waiver: no-console at src/core/shipping.ts:1`, and each item of `waivers` in `--json` has `added`. In alpha.4 a check named an added waiver only when the change also edited the law. The Claude Code plugin tells you once, at the end of a turn in which the agent added a waiver or changed or deleted a file of the law, what it added, changed and deleted.
- The Lawcheck plugin works in Codex CLI. `codex plugin marketplace add krzysztofdudek/Lawcheck` and `codex plugin add lawcheck@lawcheck-marketplace` install it, and Codex runs its hooks after you trust them in `/hooks`. The agent gets the law when a session starts, a check after each edit that sees the files of `apply_patch`, and up to three returns before it finishes. A file the agent writes through the shell gets no check after the edit, and the check before the end of the turn catches it. `lawcheck docs codex-cli` has the steps.
- The Lawcheck plugin works in GitHub Copilot CLI. `copilot plugin marketplace add krzysztofdudek/Lawcheck` and `copilot plugin install lawcheck@lawcheck-marketplace` install it. The agent gets the same law, checks and returns as in Codex, the check after an edit sees `create` and `edit`, and the plugin sends the agent back once at the end of a turn to tell you its message, since Copilot CLI gives a plugin no way to write to you. `lawcheck docs copilot-cli` has the steps.
- Cursor loads the Lawcheck plugin for Claude Code through its support for Claude Code plugins, so `claude plugin marketplace add krzysztofdudek/Lawcheck` and `claude plugin install lawcheck@lawcheck-marketplace` install it for both. No session of Cursor has run the plugin; `lawcheck docs cursor` says what was checked and what was not.
- `lawcheck doctor` names each `tsconfig.json`, `jsconfig.json`, `package.json`, `composer.json`, `compile_commands.json` or `pnpm-workspace.yaml` that a reader could not parse, with its line and column, since the uses that need such a file stay unresolved and no `may_use` list judges them. Its `readers` check shows `note`, and in `--json` it has `details`. `doctor` now reads the uses of every file to find these files, so it takes about as long as `check --full`.
- `lawcheck docs ci` has the sections "Pull requests from a fork" and "Findings in the pull request", with scripts for GitHub annotations and a GitLab code quality report, and a step that runs `lawcheck doctor` on your machine instead of in the job. `lawcheck docs adopt-in-an-existing-repository` has the section "Bring in a may_use list", for old code that already breaks the list.

### Changed

- A check of one changed file in Java, Kotlin, C#, Ruby or Rust reads what the other files declare from a cache in `.lawcheck/.local/readers/` and parses again only the files that changed and the files whose uses it reads. There was no cache in alpha.4. The output is the same with the cache and without it.
- The note about a change to the law names a type moved under another parent, such as `moves the type library from source to script`, and each pattern a change adds to `required` or `ignored` or takes off. In alpha.4 a moved type gave `edits .lawcheck/law.yaml without changing a rule or a type`.
- With a reviewer rule in the law and no reviewer in `.lawcheck/config.yaml`, `lawcheck prime` tells the agent that a plain check and CI fail on every file the rule judges, and the Claude Code plugin tells you once per session. In alpha.4 nothing said so until CI failed with `not-reviewed`.
- The `next:` lines that told the agent to edit `.lawcheck/config.yaml` now tell it to ask you, as `lawcheck prime` does.
- Every message of the Claude Code plugin starts with `Lawcheck:`, and a hook that fails prints `Lawcheck plugin:` before the cause. In alpha.4 some started with `lawcheck:`, as the tool's own output does.
- A script rule may return `line: null` for a finding about the whole file. In alpha.4 the rule was `rule-crashed`.
- The documentation is at https://docs.lawcheck.dev, and https://lawcheck.dev introduces Lawcheck. A page that alpha.4 named at `lawcheck.dev/<page>` redirects to the same page at the new address.
- Settings gives the line of `pnpm-workspace.yaml` that installs the new versions of Lawcheck and Runes on the first day after a release, `minimumReleaseAgeExclude: [lawcheck, "@chrisdudek/runes"]`, and the line of `.yarnrc.yml` for Yarn 4.15.0 and later. Supported environments and Install say what pnpm 11 and later and Yarn 4 do on that day, and link to Settings.
- `lawcheck docs languages` lists the forms each language's reader does not read, and says that a C# file uses a type of another project only when its project holds a `ProjectReference` to that project.
- The npm package and the Claude Code plugin include the MIT licence of cross-spawn, which they use on Windows.

### Fixed

- `check --full` in a large Java repository, with a law that reads the uses of every Java file, no longer stops with `memory-too-large` at the last file it parsed, such as a Kotlin build script of a few lines.
- A script rule whose background work throws after the rule's last result is `rule-crashed`: a timer it unrefs, a `node:crypto` job such as pbkdf2, or a wait on shared memory. In alpha.4 such a rule passed or failed depending on how many other files the run judged.
- When a script rule leaves a timer behind, such as `setTimeout(() => process.exit(1), 20)`, Lawcheck no longer blames the next file the rule judges: `rule-crashed` then ends with "after a call that left work running" and names no file.
- A script rule that puts a large value in a field of a finding other than `message`, `file` and `line` no longer ends the run as `memory-too-large`, since the run ignores those fields. When a run does pass its memory while a rule judges files, the error names that rule.
- A script rule that prints a lot, such as `console.log` in a loop while you debug it, no longer piles what it prints up in its own process. In alpha.4, outside Windows, the memory guard did not look there, and a rule that printed a large amount ended the run with `memory-too-large` and a `next:` line that asked you to free memory. A print now waits until Lawcheck has read it, and that wait counts toward the rule's 30 seconds.
- A caller that reads Lawcheck's standard error slower than a script rule prints now gets every line. In alpha.4, outside Windows, Lawcheck exited once its result was written, so such a caller got the first lines and the last of them cut. Lawcheck now exits once the caller has taken them all. A run that a signal, `memory-too-large` or `step-too-slow` ends does not wait.
- When a script rule throws an error with a long first line, such as a line of a minified file, `rule-crashed` shows at most 4,096 characters of it and ends with how many it left out, such as `… (cut: 96,178 more characters)`. In alpha.4 it showed the whole line, so an error of 50 MB printed 52 MB, in text and in `--json`.
- `rule-crashed` says "an error with no message" for a rule that throws an error with an empty message, where alpha.4 ended the line at the colon. For a thrown object with a `message`, such as `{ code: 'E_X', message: 'no config' }`, it shows that message, where alpha.4 showed "[object Object]". A finding whose `message` is no string, such as the number 42, gives "returns a finding whose message is the number 42, not a string", where alpha.4 said that the finding had no message.
- A plain `lawcheck check` no longer misses a file edited in the same second as the last commit or `git add` when the edit keeps the file's size. In alpha.4 it printed `PASS  nothing changed`.
- A reviewer's answer that holds a `fail` and a pass is a fail, and a pass is a bad answer when the answer also holds a verdict such as `"Fail"`, the key `verdict` twice in one object, or a `"verdict": "fail"` outside valid JSON. In alpha.4 the last object won, so a fail followed by a quoted pass read as a pass.
- A waiver whose reason holds only invisible characters, such as a zero-width space, is `waiver-without-reason`. In alpha.4 it counted as a reason, and the check passed.
- In the Claude Code plugin, a law error comes back after an edit under the same law. In alpha.4 a law broken, fixed and broken again the same way within one prompt reached the agent only the first time.
- With `runner: yarn` on Yarn 1, the plugin no longer hands the agent Yarn's closing line `info Visit https://yarnpkg.com/en/docs/cli/run for documentation about this command.` with a failing check. In alpha.4 a long output could end on that line and lose its `next:` line.
- Lawcheck ends only the processes it started. In alpha.4, on Windows, it could end a process that Windows had given the id of one of its programs or rule runners after that one ended, and leave running the processes of a program whose first process had ended. On Linux and macOS a second end could hit a new process group with the same number.
- `check`, `explain`, `try` and `doctor` in a repository that git cannot read, such as one with a corrupt `.git/index`, end with `no-git`. The message gives the line git printed and the step that repairs the repository. In alpha.4 they ended with `internal`, which asks you to report a fault of Lawcheck.
- In a sparse checkout that leaves `.lawcheck/` out, `not-initialized` says that git's index lists the law, and its `next:` line gives `git sparse-checkout add .lawcheck`. In alpha.4 it said only that there was no `.lawcheck/law.yaml`.
- `lawcheck init` in a repository whose `.gitignore` names `.lawcheck` still writes the law, and now says that git ignores it, as `lawcheck doctor` and `lawcheck prime` do. In alpha.4 none of the three said that no commit carries the law.
- `lawcheck init` at the top of a repository whose only law lies in a folder below says to write `.lawcheck/law.yaml` there by hand, with `lawcheck docs first-law`. In alpha.4 `init` sent you to `doctor`, and `doctor` sent you to the folder below.
- When `.lawcheck/law.yaml` is a folder or a symbolic link to nothing, `doctor` and `check` say `law-invalid` with the cause, and `init` stops with `file-unwritable` when `.lawcheck/.gitignore` is one. In alpha.4 `doctor` sent you to `init`, and `init` sent you back.
- A rule file that is a symbolic link gets a `rule-missing-file` message that names the link and says that Lawcheck reads no rule through one. In alpha.4 the message said that the rule had neither file.
- `lawcheck explain` says `uses:  none: the file has no script block` for a `.vue` or `.svelte` file with no script, where alpha.4 printed `uses:  read as vue`. In `--json`, `uses.language` is `null` for such a file.
- The pages of `lawcheck docs` said that a file git ignores has no type. A file git tracks keeps its type and is judged even when `.gitignore` names it, and the pages now say so.
- On Windows, a review no longer stops with `EPERM` on `.lawcheck/.local/verdicts.lock` while another run frees it.
- A review that waits its 10 seconds at `.lawcheck/.local/verdicts.lock` while another Lawcheck run holds it stops with an error that says so and tells you to let that run end. In alpha.4 its `next:` line told you to make the lock writable.
- On Windows, `lawcheck explain` no longer refuses with `usage` a file name of up to 255 characters that takes more than 255 bytes in UTF-8.

### Security

- In alpha.4 and before, every line of `.lawcheck/verdicts` counted as a pass, so a pull request could add passes for its own files and CI took them as reviews. The law now takes `signers`, each with an Ed25519 public key, and under such a law a pass counts only when a signer signed it. `lawcheck check --review` signs each pass with the key in `LAWCHECK_SIGNING_KEY`, a pass no signer signed is `not-reviewed`, and a review with no signer's key stops before its first call with `not-a-signer`. With the second check of `lawcheck docs ci`, a pull request that adds a signer of its own or takes `signers` out fails. Under a law without `signers`, Lawcheck reads the file as alpha.4 does. `lawcheck docs reviewer-rules` shows how to make a key.
- The `git fetch` that the `next:` line of `base-unreachable` names runs as one command in a POSIX shell, whatever the base is called. In alpha.4 a base with `;`, `$(`, a backtick or `&` in its name gave a line that the shell read as several commands.

## [0.1.0-alpha.4] - 2026-11-23

A script rule that uses the network now gets an error from the call itself, on every Node. On Node 24, alpha.3 let the call through. On Node 25 and later, alpha.3 passed Node's refusal to the callback, the `error` event or the promise, so a rule that handled the refusal there passed. The rule runner of alpha.4 closes the network before the rule loads. A rule that connects, listens on a port, sends over UDP, looks up a name in DNS or calls `fetch` gets the error. A rule that does not catch it is `rule-crashed`, with the message `uses the network, which is closed to script rules`.

The documentation site is now at https://lawcheck.dev, and its old address redirects there. The pages of `lawcheck docs` now say that a file outside the change can stop a plain check with exit 2, with a code such as `type-overlap` or `file-unreadable`. The alpha.3 pages said that such a file never fails a plain check. `check` judges such a file as alpha.3 does.

### Before you upgrade

A script rule that uses the network now gets an error at the call, on any Node. A handler on the callback, the `error` event or the promise no longer sees it. The rule is `rule-crashed` if it does not catch that error at the call, and the check exits with code 2. Keep what the rule needs in a file of the repository, and let the rule read that file.

## [0.1.0-alpha.3] - 2026-11-22

`lawcheck docs` lists 36 pages, where alpha.2 listed 12, and groups them in five sections. The 24 new pages include an install page, a quick start, guides for Claude Code, for other coding agents, for an existing repository and for a monorepo, a reference of every command, a page of questions and an upgrade page. The twelve topics of alpha.2 keep their names and gain detail: `lawcheck docs codes` gives every code its cause, its fix and the output of a real case. In the terminal, a link to another page prints with the command that prints that page, as in `Install (lawcheck docs install)`. The pages are also a website, at https://lawcheck.dev, and `README.md` shows one law and the finding it gives on its first screen. `check`, the readers, the plugin's hooks and the reviewer's prompt work as in alpha.2: a check gives the same results, and the verdicts in `.lawcheck/verdicts` still count.

### Before you upgrade

The text list of `lawcheck docs` has a line for each section, with the topics indented under it, so a script that reads that list meets lines it did not see before. `lawcheck docs --json` lists the topics as before, under the schema `lawcheck-docs/0`, each with its `id` and `title`.

## [0.1.0-alpha.2] - 2026-11-18

Lawcheck now reads the code with Runes 1.2.0, and `check` finds uses that alpha.1 missed. It judges them against `may_use`, so a law that passed on alpha.1 can fail now. The new uses are a Python package under a folder that `pyproject.toml` or `setup.cfg` names, a Rust `mod` with `#[path]`, a Rust path to a path dependency written without `use`, a Go module wired with a relative `replace`, a Vite, webpack or Babel alias in the forms `lawcheck docs languages` lists, `vi.mock` and `jest.mock`, a relative `<script src>` in a Vue or Svelte file, a Ruby `require` of a file in the repository, and more forms in C#. A few findings of alpha.1 go away, because the code does not reach what they named: a script inside an HTML comment of a Vue or Svelte file, and a C# name that the file declares as a value. You see fewer unresolved uses. A name imported from a relative Python module (`from .m import x`) is judged as a use of the module's file, and a C or C++ system header, a Ruby constant the repository does not declare and a Java or Kotlin member type inherited from a library now leave the repository. An alias the readers cannot follow is counted as unresolved, where alpha.1 dropped it. The install takes about 34 MB more disk, because Runes now ships its grammars.

## [0.1.0-alpha.1] - 2026-11-17

The first release of Lawcheck. You write the law of your repository in `.lawcheck/law.yaml`. The law holds the types of the files, which type may use which, and the rules each type follows. `lawcheck check` gives every file its type. It runs your script rules. It sends the rules you write in Markdown to a model for review. It reads the uses in the code of twelve languages. It judges the files a change touches against a base branch. With `--full` it lists the older breaches as debt. Each finding names its file and line. The commands `init`, `explain`, `try`, `docs`, `doctor` and `prime` go with it. They start a law, show how Lawcheck reads a file, and give the law to a coding agent. The Claude Code plugin checks each file the agent edits. It sends the agent back, up to three times, while the files of its turn break the law.

# Changelog

Lawcheck follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Before you upgrade

- A law that uses one of the new keys `signers`, `required` or `ignored`, or a rule that names a `companion`, stops alpha.4 with `law-invalid`. Install alpha.5 on every machine, CI job and git hook that checks the repository before you add one.
- A use that could name several files is now a `forbidden-use` when the `may_use` list forbids every one of them, such as a Java star import of a package whose files all have forbidden types, or a C# partial class spread over two forbidden layers. In alpha.4 such a use was only counted as unresolved, so a check that passed there can fail now. The message names each file with its type. Add one of the types to `may_use`, or waive the use with its reason. A use with one allowed file among its candidates still passes.
- The workflow of `lawcheck docs ci` now checks the second time with `lawcheck check --base "$base" --law-from "$base"`. Its alpha.4 version checked out the base's `.lawcheck/law.yaml` and `.lawcheck/rules/` and ran a plain check. When you replace those lines with the new one, a base rule that imports the project by its own `name` or imports a name that starts with `#`, and so reaches a file outside `.lawcheck/rules/`, stops that check with `rule-crashed`. The error names the import and the file. Move that file under `.lawcheck/rules/lib/` in a change of its own, merge it into the base first, and import the file by a relative path. A file git lists in `.lawcheck/node_modules` or `.lawcheck/.local` stops the same check with `law-from-packages`.
- `scope.law_changes` in `lawcheck check --json` no longer lists the waivers a change adds. A script that read them there reads the items of `waivers` whose `added` is true.
- A `check` or `try` that ends with exit 2 after it sent requests to a reviewer ends its first line with the count, such as `lawcheck: ERROR  1 error, 2 reviewer calls`, and the document `lawcheck-error/1` gains `calls_made`. A program that checks the document against a schema that refuses unknown keys has to allow `calls_made`.

### Added

- The plugins for Claude Code, Codex and GitHub Copilot CLI have a skill that writes the first law of a repository with you: `/lawcheck:setup` in Claude Code and in Copilot CLI, `$lawcheck:setup` in Codex. Only you start it, by typing the command. The agent describes the folders as types, writes the `may_use` lists that the code already keeps, and asks you before it forbids a use that the code already makes. It writes a script rule only from a rule your repository wrote down or a convention that every file keeps, and checks that each list and each rule fails on a file that breaks it. It changes nothing outside `.lawcheck/` and commits nothing. When you ask for advice, it writes `.lawcheck/advice.md` with at most three boundaries that the code does not hold today. When you name where the code should get to, it writes `.lawcheck/target.md` with that law and at most seven steps to reach it. Lawcheck reads neither file.
- Any other coding agent follows the same steps from `lawcheck docs agent-setup`: tell it "Run `lawcheck docs agent-setup` and follow it." In a folder with no law, `lawcheck prime` points the agent at that page, and the plugin tells the agent to write no law on its own. The agent tells you the command that starts the skill instead.
- A script rule can read its file's syntax tree with `await file.tree()` and the uses that `may_use` judges with `await file.uses()`, each use with the file it reaches and that file's type. Lawcheck reads either one only when the rule asks, so a rule that asks for neither costs what it cost in alpha.4. For a file over 512 KiB, a language Lawcheck cannot read or a parse that fails, the rule gets no tree and no uses, and `absent` says which of the three it was. `lawcheck explain <file> --tree` prints the tree of a real file before you write the rule, and `lawcheck docs write-a-script-rule` ends with a rule that reads the tree, so a `fetch()` in a comment is no finding.
- A reviewer rule can name a `companion`, a module in `.lawcheck/rules/lib/` that returns the files that go into the prompt of each judged file alone, such as each test with its spec. A change to the companion or to a file it returned makes the verdicts it fed stale. `lawcheck explain` runs the companion of a rule that has one, and a rule without one keeps its verdicts. `lawcheck docs reviewer-rules` has an example.
- `lawcheck check --law-from <ref>` judges a change by the law, the rules and the `package.json` files of another commit, so a change that loosens its law and breaks it fails. `lawcheck docs commands` says what it reads from that commit.
- A plain `lawcheck check` in GitHub Actions, GitLab CI and Azure Pipelines finds its base from the variables of the pull request: `GITHUB_BASE_REF`, `CI_MERGE_REQUEST_TARGET_BRANCH_NAME` (and `CI_COMMIT_BEFORE_SHA` for a push) and `SYSTEM_PULLREQUEST_TARGETBRANCH`. In alpha.4 the first run in CI stopped with `base-unreachable` until you added `--base`. A push in GitHub Actions or Azure Pipelines still needs `--base`.
- `lawcheck check --strict` judges every file as `--full` does, and a finding of an `enforced` rule in old code fails the run with exit 1. A team that paid its debt can keep it at zero.
- `lawcheck check --sarif <file>` also writes the findings in SARIF 2.1.0 for GitHub code scanning. `lawcheck docs ci` has the step that uploads it.
- The law takes two keys at the top, `required` and `ignored`, each a list of patterns. A text file under `required` that no type takes is the new finding `untyped-file`, so code an agent puts in a new folder beside the layers no longer escapes the law. A file under `ignored` has no type. `lawcheck explain` and `lawcheck prime` name both.
- `lawcheck check` names each waiver that a change adds in a note under the first line, such as `note: this change adds 1 waiver: no-console at src/core/shipping.ts:1`, and each item of `waivers` in `--json` has `added`. In alpha.4 a check named an added waiver only when the change also edited the law. The Claude Code plugin tells you once, at the end of a turn in which the agent added a waiver or changed or deleted a file of the law, what it added, changed and deleted.
- The Lawcheck plugin works in Codex CLI. `codex plugin marketplace add krzysztofdudek/Lawcheck` and `codex plugin add lawcheck@lawcheck-marketplace` install it, and Codex runs its hooks after you trust them in `/hooks`. The agent gets the law when a session starts, a check after each edit that sees the files of `apply_patch`, and up to three returns before it finishes. A file the agent writes through the shell gets no check after the edit, and the check before the end of the turn catches it. `lawcheck docs codex-cli` has the steps.
- The Lawcheck plugin works in GitHub Copilot CLI. `copilot plugin marketplace add krzysztofdudek/Lawcheck` and `copilot plugin install lawcheck@lawcheck-marketplace` install it. The agent gets the same law, checks and returns as in Codex, the check after an edit sees `create` and `edit`, and the plugin sends the agent back once at the end of a turn to tell you its message, since Copilot CLI gives a plugin no way to write to you. `lawcheck docs copilot-cli` has the steps.
- Cursor runs the Lawcheck plugin for Claude Code, so `claude plugin marketplace add krzysztofdudek/Lawcheck` and `claude plugin install lawcheck@lawcheck-marketplace` install it for both. The check before the agent finishes runs only when `.cursor/hooks.json` holds `{"version": 1, "hooks": {"beforeSubmitPrompt": [{"command": "echo {}"}], "stop": [{"command": "echo {}"}]}}`. No session of Cursor ran the plugin, because that needs a Cursor account; `lawcheck docs cursor` says what was checked and what was not.
- `lawcheck doctor` names each `tsconfig.json`, `jsconfig.json`, `package.json`, `composer.json`, `compile_commands.json` or `pnpm-workspace.yaml` that a reader could not parse, with its line and column, since the uses that need such a file stay unresolved and no `may_use` list judges them. Its `readers` check shows `note`, and in `--json` it has `details`. `doctor` now reads the uses of every file to find these files, so it takes about as long as `check --full`.
- `lawcheck docs ci` has the sections "Pull requests from a fork" and "Findings in the pull request", with scripts for GitHub annotations and a GitLab code quality report, and a step that runs `lawcheck doctor` on your machine instead of in the job. `lawcheck docs adopt-in-an-existing-repository` has the section "Bring in a may_use list", for old code that already breaks the list.

### Changed

- A check of one changed file in Java, Kotlin, C#, Ruby or Rust parses again only the files that changed, from a cache in `.lawcheck/.local/readers/`. In alpha.4 such a check took 6 seconds in a Java repository of 3,267 files and 4 in a C# repository of 951; with the cache, about 0.3 each. The output is the same with the cache and without it.
- The note about a change to the law names a type moved under another parent, such as `moves the type library from source to script`, and each pattern a change adds to `required` or `ignored` or takes off. In alpha.4 a moved type gave `edits .lawcheck/law.yaml without changing a rule or a type`.
- With a reviewer rule in the law and no reviewer in `.lawcheck/config.yaml`, `lawcheck prime` tells the agent that a plain check and CI fail on every file the rule judges, and the Claude Code plugin tells you once per session. In alpha.4 nothing said so until CI failed with `not-reviewed`.
- The `next:` lines that told the agent to edit `.lawcheck/config.yaml` now tell it to ask you, as `lawcheck prime` does.
- Every message of the Claude Code plugin starts with `Lawcheck:`, and a hook that fails prints `Lawcheck plugin:` before the cause. In alpha.4 some started with `lawcheck:`, as the tool's own output does.
- A script rule may return `line: null` for a finding about the whole file. In alpha.4 the rule was `rule-crashed`.
- The documentation is at https://docs.lawcheck.dev, and https://lawcheck.dev introduces Lawcheck. A page that alpha.4 named at `lawcheck.dev/<page>` redirects to the same page at the new address.
- The pages Settings, Supported environments and Install say what pnpm 11 and later and Yarn 4 do on the first day after a release, and give the line of `pnpm-workspace.yaml` that installs the new versions: `minimumReleaseAgeExclude: [lawcheck, "@chrisdudek/runes"]`.
- `lawcheck docs languages` lists the forms each language's reader does not read, and says that a C# file uses a type of another project only when its project holds a `ProjectReference` to that project.
- The npm package and the Claude Code plugin include the MIT licence of cross-spawn, which they use on Windows.

### Fixed

- `check --full` in a large Java repository, with a law that reads the uses of every Java file, no longer stops with `memory-too-large` at the last file it parsed, such as a Kotlin build script of a few lines.
- A script rule whose background work throws after the rule's last result is `rule-crashed`: a timer it unrefs, a `node:crypto` job such as pbkdf2, or a wait on shared memory. In alpha.4 such a rule passed or failed depending on how many other files the run judged.
- A script rule that leaves a timer behind, such as `setTimeout(() => process.exit(1), 20)`, is no longer blamed on the next file it judges: `rule-crashed` then ends with "after a call that left work running" and names no file.
- A script rule that puts a large value in a field of a finding other than `message`, `file` and `line` no longer ends the run as `memory-too-large`, since the run ignores those fields. When a run does pass its memory while a rule judges files, the error names that rule.
- A plain `lawcheck check` no longer misses a file edited in the same second as the last commit or `git add` when the edit keeps the file's size. In alpha.4 it printed `PASS  nothing changed`.
- A reviewer's answer that holds a `fail` and a pass is a fail, and a pass is a bad answer when the answer also holds a verdict such as `"Fail"`, the key `verdict` twice in one object, or a `"verdict": "fail"` outside valid JSON. In alpha.4 the last object won, so a fail followed by a quoted pass read as a pass.
- In the Claude Code plugin, a law error comes back after an edit under the same law. In alpha.4 a law broken, fixed and broken again the same way within one prompt reached the agent only the first time.
- With `runner: yarn` on Yarn 1, a failing check no longer hands the agent Yarn's closing line `info Visit https://yarnpkg.com/en/docs/cli/run for documentation about this command.` in place of the `next:` line.
- Lawcheck ends only the processes it started. In alpha.4, on Windows, it could end a process that Windows had given the id of one of its programs or rule runners after that one ended, and leave running the processes of a program whose first process had ended. On Linux and macOS a second end could hit a new process group with the same number.
- `check`, `explain`, `try` and `doctor` in a repository that git cannot read, such as one with a corrupt `.git/index`, end with `no-git`. The message gives the line git printed and the step that repairs the repository. In alpha.4 they ended with `internal`, which asks you to report a fault of Lawcheck.
- `lawcheck init` in a repository whose `.gitignore` names `.lawcheck` still writes the law, and now says that git ignores it, as `lawcheck doctor` and `lawcheck prime` do. In alpha.4 none of the three said that no commit carries the law.
- `lawcheck init` at the top of a repository whose only law lies in a folder below says to write `.lawcheck/law.yaml` there by hand, with `lawcheck docs first-law`. In alpha.4 `init` sent you to `doctor`, and `doctor` sent you to the folder below.
- When `.lawcheck/law.yaml` is a folder or a symbolic link to nothing, `doctor` and `check` say `law-invalid` with the cause, and `init` stops with `file-unwritable` when `.lawcheck/.gitignore` is one. In alpha.4 `doctor` sent you to `init`, and `init` sent you back.
- A rule file that is a symbolic link gets a `rule-missing-file` message that names the link and says that Lawcheck reads no rule through one. In alpha.4 the message said that the rule had neither file.
- `lawcheck explain` says `uses:  none: the file has no script block` for a `.vue` or `.svelte` file with no script, where alpha.4 printed `uses:  read as vue`. In `--json`, `uses.language` is `null` for such a file.
- The pages of `lawcheck docs` said that a file git ignores has no type. A file git tracks keeps its type and is judged even when `.gitignore` names it, and the pages now say so.
- On Windows, a review no longer stops with `EPERM` on `.lawcheck/.local/verdicts.lock` while another run frees it.
- On Windows, `lawcheck explain` no longer refuses with `usage` a file name of up to 255 characters that takes more than 255 bytes in UTF-8.

### Security

- In alpha.4 and before, every line of `.lawcheck/verdicts` counted as a pass, so a pull request could add passes for its own files and CI took them as reviews. The law now takes `signers`, each with an Ed25519 public key, and under such a law a pass counts only when a signer signed it. `lawcheck check --review` signs each pass with the key in `LAWCHECK_SIGNING_KEY`, a pass no signer signed is `not-reviewed`, and a review with no signer's key stops before its first call with `not-a-signer`. With the second check of `lawcheck docs ci`, a pull request that adds a signer of its own or takes `signers` out fails. A law without `signers` reads the file as alpha.4 does. `lawcheck docs reviewer-rules` shows how to make a key.
- The `git fetch` that the `next:` line of `base-unreachable` names runs as one command in a POSIX shell, whatever the base is called. In alpha.4 a base with `;`, `$(`, a backtick or `&` in its name gave a line that the shell read as several commands.

## [0.1.0-alpha.4] - 2026-11-23

A script rule that uses the network now gets an error from the call itself, on every Node. On Node 24, alpha.3 let the call through. On Node 25 and later, alpha.3 passed Node's refusal to the callback, the `error` event or the promise, so a rule that handled the refusal there passed. The rule runner of alpha.4 closes the network before the rule loads. A rule that connects, listens on a port, sends over UDP, looks up a name in DNS or calls `fetch` gets the error. A rule that does not catch it is `rule-crashed`, with the message `uses the network, which is closed to script rules`.

The documentation site is now at https://lawcheck.dev, and its old address redirects there. The pages of `lawcheck docs` now say that a file outside the change can stop a plain check with exit 2, with a code such as `type-overlap` or `file-unreadable`. The alpha.3 pages said that such a file never fails a plain check. `check` judges such a file as alpha.3 does.

### Before you upgrade

A script rule that uses the network now gets an error at the call, on any Node. A handler on the callback, the `error` event or the promise no longer sees it. The rule is `rule-crashed` if it does not catch that error at the call, and the check exits with code 2. Keep what the rule needs in a file of the repository, and let the rule read that file.

## [0.1.0-alpha.3] - 2026-11-22

`lawcheck docs` lists 36 pages, where alpha.2 listed 12, and groups them in five sections. The 24 new pages include an install page, a quick start, guides for Claude Code, for other coding agents, for an existing repository and for a monorepo, a reference of every command, a page of questions and an upgrade page. The twelve topics of alpha.2 keep their names and gain detail: `lawcheck docs codes` gives every code its cause, its fix and the output of a real case. In the terminal, a link to another page prints with the command that prints that page, as in `Install (lawcheck docs install)`. The pages are also a website, at https://lawcheck.dev, and `README.md` shows one law and the finding it gives on its first screen. `check`, the readers, the plugin's hooks and the reviewer's prompt work as in alpha.2: a check gives the same results, and the verdicts in `.lawcheck/verdicts` still count.

### Before you upgrade

The text list of `lawcheck docs` has a line for each section, with the topics indented under it, so a script that reads that list meets lines it did not see before. `lawcheck docs --json` lists the topics as before, under the schema `lawcheck-docs/0`, each with its `id` and `title`.

## [0.1.0-alpha.2] - 2026-11-18

Lawcheck now reads the code with Runes 1.2.0, and `check` finds uses that alpha.1 missed. It judges them against `may_use`, so a law that passed on alpha.1 can fail now. The new uses are a Python package under a folder that `pyproject.toml` or `setup.cfg` names, a Rust `mod` with `#[path]`, a Rust path to a path dependency written without `use`, a Go module wired with a relative `replace`, a Vite, webpack or Babel alias in the forms `lawcheck docs languages` lists, `vi.mock` and `jest.mock`, a relative `<script src>` in a Vue or Svelte file, a Ruby `require` of a file in the repository, and more forms in C#. A few findings of alpha.1 go away, because the code does not reach what they named: a script inside an HTML comment of a Vue or Svelte file, and a C# name that the file declares as a value. You see fewer unresolved uses. A name imported from a relative Python module (`from .m import x`) is judged as a use of the module's file, and a C or C++ system header, a Ruby constant the repository does not declare and a Java or Kotlin member type inherited from a library now leave the repository. An alias the readers cannot follow is counted as unresolved, where alpha.1 dropped it. The install takes about 34 MB more disk, because Runes now ships its grammars.

## [0.1.0-alpha.1] - 2026-11-17

The first release of Lawcheck. You write the law of your repository in `.lawcheck/law.yaml`: the types of its files, which type may use which, and the rules each type follows. `lawcheck check` gives every file its type, runs your script rules, sends the rules you write in Markdown to a model for review, and reads the uses in the code of twelve languages. It judges the files a change touches against a base branch, lists the older breaches as debt with `--full`, and names the file and line of each one. The commands `init`, `explain`, `try`, `docs`, `doctor` and `prime` start a law, show how Lawcheck reads a file, and give the law to a coding agent. The Claude Code plugin checks each file the agent edits and sends the agent back, up to three times, while the files of its turn break the law.

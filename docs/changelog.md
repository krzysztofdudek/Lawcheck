# Changelog

Lawcheck follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

The Claude Code plugin and the Codex plugin have a skill that writes the first law of a repository with you: `/lawcheck:setup` in Claude Code, `$lawcheck:setup` in Codex. Only you start it, by typing the command; the agent never starts it by itself. The agent describes the folders as types, counts which type uses which today, and writes `may_use` lists that the code already keeps. Before it forbids a use that the code already makes, it asks you and gives three ways: keep the use allowed, forbid it and count its files as debt, or put those files in a type of their own. It writes a script rule only from a rule your repository wrote down or a convention that every file keeps, and a rule about code reads the file's syntax tree, so a word in a comment is no finding. A rule that the old code breaks waits for your answer: enforced, advisory or left out. It checks that each list and each rule fails on a file that breaks it. It changes nothing outside `.lawcheck/` and commits nothing. When you ask for advice in the words you type with the command, it writes `.lawcheck/advice.md`: at most three boundaries or rules that the code does not hold today, each with its evidence and its counts. When you name where the code should get to, it writes `.lawcheck/target.md`: the law the code should reach, how far the code is from it today, and at most seven steps to get there. Lawcheck reads neither file, and a line goes into the law only when you say yes to that item or that step. In alpha.4 the plugin told the agent only to wait for your word before `lawcheck init`, and `init` writes an empty law.

Any other coding agent follows the same steps from the page `lawcheck docs agent-setup`: tell it "Run `lawcheck docs agent-setup` and follow it." In a folder with no law, `lawcheck prime` now points the agent at that page, and the plugin tells it to write no law on its own and to point you at the command of the skill.

A script rule can read the syntax tree and the uses of its file. `await file.tree()` gives the tree that the grammar of the file's language parses, with each node's type, field, place in the text, line, column and children. `await file.uses()` gives the uses that `may_use` judges, each with the file it reaches and that file's type. Lawcheck reads either one only when the rule asks, so a rule that asks for neither costs what it cost in alpha.4. A file over 512 KiB, a language with no reader and a reader that fails give the rule an `absent` reason instead of an error of the run. The grammars are those of Runes 1.2.0, the same as in alpha.4. `lawcheck docs script-rules` lists each grammar's version and says what a new grammar may change.

A reviewer rule can name a companion, a module in `.lawcheck/rules/lib/` that returns, for each file the reviewer judges, the files that go into that file's prompt alone. A rule can then send each test with its spec, or each handler with its contract. In alpha.4, `context` sent the same files with every judged file, so such a rule had to send every pair to every file. The companion gets the same `file` and `repo` as a script rule, `file.tree()` and `file.uses()` included, and runs in the same runner with the same limits. A change to the companion or to a file it returned makes the verdicts it fed stale, its files count toward `reviewer.max_chars`, and a path that names no file git lists stops the run with `rule-crashed`. The files it returns decide each review, so `lawcheck explain` now runs the companion of a rule that has one. `lawcheck explain --rule` names the companion, and its JSON gains `companion`. A rule without a companion keeps its verdicts. `lawcheck docs reviewer-rules` has an example.

A plain `lawcheck check` in GitHub Actions, GitLab CI and Azure Pipelines now finds its base from the variables of the pull request: `GITHUB_BASE_REF`, `CI_MERGE_REQUEST_TARGET_BRANCH_NAME` (and `CI_COMMIT_BEFORE_SHA` for a push to a branch) and `SYSTEM_PULLREQUEST_TARGETBRANCH`. Before, the first run in CI stopped with `base-unreachable` until you added `--base` from the docs. `--base` and `LAWCHECK_BASE` still come first, and the job still has to fetch the history of the base. GitHub Actions and Azure Pipelines set no variable for the commit before a push, so a push there still needs `--base`. The recipes for GitLab CI and Azure Pipelines in `lawcheck docs ci` lose the flag.

`lawcheck check --strict` judges every file as `--full` does, and a finding in old code fails the run when the same finding in the change would. A finding of an `enforced` rule in an old file is then an error with exit 1, and a finding of an `advisory` rule stays a warning. A team that paid its debt can keep it at zero. Without `--strict`, debt fails nothing, as before.

A check of one changed file in Java, Kotlin, C#, Ruby or Rust no longer parses every file of the language. `check` keeps what each file declares in `.lawcheck/.local/readers/`, and a later check parses again only the files that changed. In a Java repository of 3,267 files, a check of one changed file took 6 seconds in alpha.4 and takes about 0.3 seconds with the cache. In a C# repository of 951 files, it took 4 seconds and takes about 0.3 seconds. A check with the cache gives the same output as a check without it. `lawcheck docs languages` says when Lawcheck does not trust the cache. Lawcheck also stops counting the memory a run gains after its last parse against the last file it parsed. In alpha.4, `check --full` in that Java repository, with a law that reads the uses of every Java file, stopped with `memory-too-large` at a Kotlin build script of a few lines, the last file it parsed.

The law takes two new keys at the top, `required` and `ignored`, each a list of patterns. A text file under `required` that no type takes is the new finding `untyped-file`: an error in the change, a warning in debt. Before, such a file was judged by no rule and nothing said so, so an agent that put code in a new folder beside the layers put it outside the whole law. A file under `ignored` has no type, even when a type's `paths` match it. `lawcheck explain` names both, `lawcheck prime` lists them and leaves a new pattern of `ignored` to your word, as it does in every law with `may_use`, and the note about a change to the law names each pattern a change adds to them or takes off, such as `adds src/gen/** to ignored`. A law without the two keys works as in alpha.4.

A use that could name several files is now a `forbidden-use` when the `may_use` list forbids every one of them, such as a Java star import of a package whose files are all of forbidden types, or a C# partial class spread over two forbidden layers. The message names each file with its type. In alpha.4 such a use was only counted as unresolved and the check passed. A use with one allowed file among its candidates still passes, and every such use stays in the unresolved list.

A change that moves a type under another parent is now named in the note about a change to the law, such as `moves the type library from source to script`. In alpha.4 the note said `edits .lawcheck/law.yaml without changing a rule or a type`, though the files of the moved type could lose their rules and their `may_use` list.

`lawcheck check` names every waiver that a change adds, in a note under the first line, such as `note: this change adds 1 waiver: no-console at src/core/shipping.ts:1`. A waiver that the base already holds is not named. In alpha.4, a check named an added waiver only when the same change also edited the law, inside the note about the law. In `--json`, each item of `waivers` has `added`. The Claude Code plugin tells you once, at the end of a turn in which the agent added a waiver or changed or deleted `.lawcheck/law.yaml`, `.lawcheck/config.yaml` or a rule file, what it added, changed and deleted. It does not send the agent back.

`lawcheck docs adopt-in-an-existing-repository` gains the section "Bring in a may_use list". A `may_use` list has no advisory status, so the section says how to close one on old code that already breaks it: the list goes first on the clean types, each old use gets a waiver with its reason, and the waivers are paid back one at a time.

`lawcheck doctor` now names each configuration file that a reader could not read. When a `tsconfig.json`, `jsconfig.json`, `package.json`, `composer.json`, `compile_commands.json` or `pnpm-workspace.yaml` does not parse, the reader goes on without it. The uses that need the file are unresolved, so a law that forbids such a use looked kept. The `readers` check now shows `note` and prints one line for each such file, with the line and column of the failure when the parser gives them. In `--json`, the check has a `details` list. To find these files, `doctor` reads the uses as `check --full` does, so it now takes about as long.

`lawcheck docs languages` now says that a C# file uses a type of another project only when its project holds a `ProjectReference` to that project. Without one, the use is unresolved and no `may_use` list judges it. The page also lists the forms of each language that no reader reads.

`lawcheck docs ci` has two new sections and a new step. "Pull requests from a fork" says that the job of a fork needs no secret, that the check must not run on `pull_request_target`, what a contributor without a reviewer does about `not-reviewed`, and that the job trusts the lines a pull request adds to `.lawcheck/verdicts`. "Findings in the pull request" gives a script that turns `check --json` into GitHub annotations and one that writes a GitLab code quality report. It also says that a warning shows only in the log of a job and that a plain check prints no debt. Step 4 of "Reviewer rules in CI" says to run `lawcheck doctor` on your machine: in a job that reads the committed verdicts it fails with exit 2 where `check` passes.

The `git fetch` that the `next:` line of `base-unreachable` names now runs as one command in a POSIX shell, or is not printed, whatever the branch is called. In alpha.4 a base with `;`, `$(`, a backtick or `&` in its name gave a line that the shell read as several commands. The command quotes such a name. A name that git refuses as a branch name or that holds a line break gets `git fetch --unshallow`, or no command on a full clone. Lawcheck runs nothing itself, and the same line is in `next.command` of the JSON.

With a reviewer rule in the law and no reviewer in `.lawcheck/config.yaml`, `lawcheck prime` now tells the agent that a plain check and CI fail on every file the rule judges, and to tell you. The Claude Code plugin also sends you that message itself, once per session. In alpha.4 every hook stayed silent, the agent finished its turn, and the check in CI failed with `not-reviewed`.

The `next:` lines that told the agent to edit `.lawcheck/config.yaml` now tell it to ask you, since `lawcheck prime` leaves every edit of that file to you. This holds for the line after `config-invalid`, after a reviewer that gives no answer in time, after a model the provider does not find, after a reviewer program such as `claude` that fails, and in `lawcheck doctor` after a model that answers the test call wrong and after a `runner` whose program is not on the `PATH`.

When git ignores `.lawcheck/law.yaml`, `lawcheck prime` now says that no commit carries the law, so an agent tells you in every session, not only in the one that ran `lawcheck init`. In alpha.4 only `init` and `lawcheck doctor` said it.

`lawcheck docs write-a-script-rule` gains a last step that rewrites the rule with the syntax tree of the file, so a `fetch()` in a comment is no longer reported.

In the Claude Code plugin, a law error that the agent was shown once comes back after an edit that Lawcheck could check. In alpha.4, a law broken, fixed and broken again the same way within one prompt reached the agent only the first time.

Every message the Claude Code plugin sends you, and every text it gives the agent after an edit or at the end of a turn, now starts with `Lawcheck:`. In alpha.4 some started with `lawcheck:`, as the tool's own output does, and one read `lawcheck: lawcheck check could not judge`. A hook that fails now prints `Lawcheck plugin:` before the cause. A reason that ends in a full stop no longer gets a second one, the text the agent gets says `... 1 more line not shown` for one line, and `lawcheck prime` says `1 more root type`.

The npm package and the Claude Code plugin now include the MIT licence of cross-spawn, whose escaping of arguments for `cmd.exe` they use on Windows.
A plain `lawcheck check` no longer misses a file edited in the same second as the last commit or `git add`, when the edit keeps the file's size. In alpha.4 the check printed `PASS  nothing changed` while `git status` showed the file as modified.

The Lawcheck plugin now works in Codex CLI. `codex plugin marketplace add krzysztofdudek/Lawcheck` and `codex plugin add lawcheck@lawcheck-marketplace` install it, and Codex runs its hooks after you trust them in `/hooks`. The agent gets the law when a session starts, a check after each `apply_patch`, and up to three returns before it finishes, as in Claude Code. A file the agent writes through the shell gets no check after the edit, and the check before the end of the turn catches it. `LAWCHECK_PLUGIN_CHECK_AFTER_EDIT` and `LAWCHECK_PLUGIN_CHECK_BEFORE_STOP` switch the two checks off. In alpha.4 Codex got the law only through a line in its instructions file. `lawcheck docs codex-cli` has the steps.
### Before you upgrade

`scope.law_changes` in `lawcheck check --json` no longer lists the waivers a change adds. A script that read them there reads the items of `waivers` whose `added` is true.
`lawcheck init` in a repository whose `.gitignore` names `.lawcheck` still writes the law, and now says that git ignores it, so no commit carries it and no other checkout has it. The output gains a `note:` line, and in `--json` the `next.text` starts with the same warning. `lawcheck doctor` shows its `law` check as `note` and names `git check-ignore -v .lawcheck/law.yaml`, which finds the line to remove. In alpha.4, both passed and said nothing.

The pages of `lawcheck docs` said that a file git ignores has no type. That holds only for a file git does not track. A file git tracks keeps its type and is judged even when `.gitignore` names it, as `lawcheck explain` shows. The pages now say so.
A script rule may return `line: null` for a finding about the whole file. In alpha.4 the rule was `rule-crashed`. A string such as `'2'`, a bigint or `1.5` still crashes the rule, with a message that names the value.

A script rule whose timer throws after the rule's last result is now `rule-crashed` also when the rule unrefs the timer, with `unref()` or with `ref: false` of `node:timers/promises`, and when the throw follows an asynchronous wait on shared memory that ends after that result. In alpha.4 such a rule passed, because Lawcheck waited neither for an unreferenced timer nor for such a wait.

When a reviewer's answer holds two verdict objects and one of them is a `fail`, the answer is that fail. In alpha.4 the last object won, so a fail followed by a quoted pass read as a pass. A pass is now a bad answer when an object of the answer holds the key `verdict` twice, or when another object holds a verdict that is neither `pass` nor `fail`, such as `"Fail"`. In alpha.4 both read as a pass.

A `check` or `try` that ends with exit 2 after it sent requests to a reviewer now says how many. The first line ends with the count, such as `lawcheck: ERROR  1 error, 2 reviewer calls`, and the JSON document `lawcheck-error/1` gains `calls_made` when the count is above 0. A program that checks the document against a schema that refuses unknown keys has to allow `calls_made`.

## [0.1.0-alpha.4] - 2026-11-23

A script rule that uses the network now gets an error from the call itself, on every Node. On Node 24, alpha.3 let the call through. On Node 25 and later, alpha.3 passed Node's refusal to the callback, the `error` event or the promise, so a rule that handled the refusal there passed. The rule runner of alpha.4 closes the network before the rule loads. A rule that connects, listens on a port, sends over UDP, looks up a name in DNS or calls `fetch` gets the error. A rule that does not catch it is `rule-crashed`, with the message `uses the network, which is closed to script rules`.

The documentation site is now at https://lawcheck.dev, and its old address redirects there. The pages of `lawcheck docs` now say that a file outside the change can stop a plain check with exit 2, with a code such as `type-overlap` or `file-unreadable`. The alpha.3 pages said that such a file never fails a plain check. `check` judges such a file as alpha.3 does.

### Before you upgrade

A script rule that uses the network now gets an error at the call, on any Node. A handler on the callback, the `error` event or the promise no longer sees it. The rule is `rule-crashed` if it does not catch that error at the call, and the check exits with code 2. Keep what the rule needs in a file of the repository, and let the rule read that file.

## [0.1.0-alpha.3] - 2026-11-22

`lawcheck docs` lists 36 pages, where alpha.2 listed 12, and groups them in five sections. The 24 new pages include an install page, a quick start, guides for Claude Code, for other coding agents, for an existing repository and for a monorepo, a reference of every command, a page of questions and an upgrade page. The twelve topics of alpha.2 keep their names and gain detail: `lawcheck docs codes` gives every code its cause, its fix and the output of a real case. In the terminal, a link to another page prints with the command that prints that page, as in `Install (lawcheck docs install)`. The pages are also a website, at https://lawcheck.dev, and `README.md` shows one law and the finding it gives on its first screen. `check`, the readers, the plugin's hooks and the reviewer's prompt work as in alpha.2: a check gives the same results, and the verdicts in `.lawcheck/verdicts` still count.

### Before you upgrade

The text list of `lawcheck docs` has a line for each section, with the topics indented under it, so a script that reads that list meets lines it did not see before. `lawcheck docs --json` lists the topics as before, under the schema `lawcheck-docs/0`, each with its `id` and `title`.

## [0.1.0-alpha.2] - 2026-11-18

Lawcheck now reads the code with Runes 1.2.0, and `check` finds uses that alpha.1 missed. It judges them against `may_use`, so a law that passed on alpha.1 can fail now. The new uses are a Python package under a folder that `pyproject.toml` or `setup.cfg` names, a Rust `mod` with `#[path]`, a Rust path to a path dependency written without `use`, a Go module wired with a relative `replace`, a Vite, webpack or Babel alias in the forms `lawcheck docs languages` lists, `vi.mock` and `jest.mock`, a relative `<script src>` in a Vue or Svelte file, a Ruby `require` of a file in the repository, and more forms in C#. A few findings of alpha.1 go away, because the code does not reach what they named: a script inside an HTML comment of a Vue or Svelte file, and a C# name that the file declares as a value. You see fewer unresolved uses. A name imported from a relative Python module (`from .m import x`) is judged as a use of the module's file, and a C or C++ system header, a Ruby constant the repository does not declare and a Java or Kotlin member type inherited from a library now leave the repository. An alias the readers cannot follow is counted as unresolved, where alpha.1 dropped it. The install takes about 34 MB more disk, because Runes now ships its grammars.

## [0.1.0-alpha.1] - 2026-11-17

The first release of Lawcheck. You write the law of your repository in `.lawcheck/law.yaml`: the types of its files, which type may use which, and the rules each type follows. `lawcheck check` gives every file its type, runs your script rules, sends the rules you write in Markdown to a model for review, and reads the uses in the code of twelve languages. It judges the files a change touches against a base branch, lists the older breaches as debt with `--full`, and names the file and line of each one. The commands `init`, `explain`, `try`, `docs`, `doctor` and `prime` start a law, show how Lawcheck reads a file, and give the law to a coding agent. The Claude Code plugin checks each file the agent edits and sends the agent back, up to three times, while the files of its turn break the law.
